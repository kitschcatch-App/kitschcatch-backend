# 사용자 차단

## HTTP 계약

모든 요청은 액세스 토큰이 필요하며, 요청자는 JWT에서 결정한다.

| 요청 | 성공 응답의 data |
| --- | --- |
| `POST /api/users/{userId}/block` | `{ "userId": 25, "blockedByMe": true }` |
| `DELETE /api/users/{userId}/block` | `{ "userId": 25, "blockedByMe": false }` |
| `GET /api/users/me/blocks?page=0&size=20` | `content`, `page`, `size`, `totalElements`, `totalPages` |

차단·해제는 본문 없이 호출하고 반복 요청도 200이다. 반복 차단은 최초 차단 시각을 유지한다. 해제 후 다시 차단하면 새 관계와 시각을 기록한다. 자기 자신 또는 유효하지 않은 ID는 400 `COMMON_002`이다. 새 차단에서 대상이 없거나 탈퇴했으면 404 `USER_001`이고, 없는 관계의 해제는 200이다.

목록에는 로그인한 사용자가 직접 차단한 대상만 담는다. 항목은 `userId`, `nickname`, `profileImageUrl`, `blockedAt`이다. 최신 차단 시각과 관계 ID의 내림차순으로 정렬한다. 페이지는 0부터 시작하며 최대 10000이고, 크기는 1~100이다. 범위를 벗어나면 400 `COMMON_001`을 반환한다. 이미지가 있으면 기존 프로필의 GET 서명 URL을 발급하며, 만료 시 목록을 다시 조회한다.

## 차단과 해제의 효과

- A가 B를 차단하면 A → B 한 건을 저장하고 기존 팔로우는 양방향으로 삭제한다. 어느 방향이든 차단 관계가 있으면 양쪽의 새 팔로우와 채팅을 제한한다. HTTP 요청은 403 `USER_009`를 반환하며, STOMP 전송은 저장과 방송을 하지 않는다. 응답은 상대의 차단 방향을 알려주지 않는다.
- A의 해제는 A → B 관계만 삭제한다. 반대 방향이 남으면 전송 제한도 유지한다. 팔로우를 다시 맺으려면 새 요청이 필요하다.
- 채팅 제한은 상품에 관계없이 적용된다. 새 방 만들기와 기존 방 재사용 요청, HTTP·STOMP 텍스트, 이미지 업로드 URL 발급, 이미지 등록을 모두 검사한다.
- 기존 방과 메시지는 참여자가 조회할 수 있다. 이미 받은 메시지는 읽음 처리할 수 있고 `unreadCount`와 이력의 `isRead`는 실제 저장 값을 반환한다. 차단 중에는 메시지와 실시간 읽음 이벤트를 구독 세션에 전달하지 않는다.
- 채팅방 목록·상세의 `blockedByMe`는 요청자가 직접 설정한 차단이다. `canSendMessage`는 현재 전송 가능 여부이며, 차단 또는 상대의 탈퇴 시 false다. 공개 프로필의 `blockedByMe`와 `canFollow`도 요청자 기준이다. 해제 응답을 받은 뒤 이 상태를 다시 조회할 수 있다.
- 아직 발송되지 않은 두 사람의 채팅 푸시는 `SKIPPED / USER_BLOCKED`로 전환한다. 해제해도 해당 작업은 재발송하지 않는다. 기존 알림함, 거래 기능과 거래 알림, 공개 콘텐츠의 조회 정책은 유지한다.
- 탈퇴 시 해당 사용자 양방향의 차단 관계를 정리한다.

## 경합과 배포

차단·해제, 팔로우, 채팅 저장은 사용자 ID 오름차순으로 동일한 행 잠금을 사용한다. 잠금 뒤 최신 상태를 재확인하며, 차단 저장·팔로우 삭제·대기 푸시 발송 제외는 함께 커밋하거나 롤백한다. 차단보다 먼저 저장한 메시지는 이력에 남고, 차단이 먼저 커밋되면 후속 저장을 거부한다. S3 확인은 잠금 밖에서 실행하며, 이전에 받은 PUT URL로 파일을 올려도 최종 메시지 등록에서 차단을 확인한다.

STOMP는 정의된 채팅 목적지와 참여자만 허용한다. 이미 열린 구독도 서버의 전달 직전에 현재 관계를 조회한다. 이미 네트워크나 푸시 제공자에 전달된 이벤트는 회수할 수 없다.

기존 팔로우·채팅·알림 테이블이 있는 대상 DB에 [089_user_blocks.sql](../src/main/resources/db/manual/089_user_blocks.sql)을 앱 배포 전에 적용한다. 해당 스크립트는 차단 테이블과 채팅 푸시 조회에 필요한 인덱스를 추가한다. GitHub CI는 격리된 PostgreSQL 스키마에서 SQL을 두 번 적용한 뒤 HTTP·STOMP, 차단과 메시지·팔로우·이미지·푸시의 동시 요청을 검증한다. 푸시와 이미지 통합 테스트는 외부 제공자 대신 테스트 대역을 사용한다.
