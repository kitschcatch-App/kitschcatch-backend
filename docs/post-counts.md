# 상품 하트·문의방 수와 관심 목록 시각

이슈 #77, 브랜치 `feat/77`, 기준 develop `69f3169`.

## 응답 계약

공통 `PostResponse`에 숫자형 `favoriteCount`, `chatRoomCount`를 추가한다. 상세 `GET /api/posts/{postId}`, 검색 `GET /api/posts`, 본인·판매자 상품 목록, 상품 등록·수정 응답에 적용한다. 신규 생성 응답은 아직 다른 요청에 공개되지 않은 상품이므로 두 값이 0이다. 수정 및 조회 응답은 실제 저장 관계를 집계한다.

`GET /api/users/me/favorite-posts`의 각 content 항목에도 두 집계값과 `createdAt`을 추가한다. `createdAt`은 상품 최초 등록 시각, 기존 `favoritedAt`은 현재 관심 관계의 등록 시각이다. 날짜 형식은 기존 상품 응답과 동일하다. 정렬은 관심 관계의 createdAt·ID 역순을 유지한다. 삭제 상품 제외, 예약·판매 완료 상품 포함, 대표 이미지 GET 서명 계약을 유지한다.

```json
{
  "id": 10,
  "createdAt": "2026-01-01T09:00:00",
  "favoritedAt": "2026-11-04T10:00:00",
  "favoriteCount": 3,
  "chatRoomCount": 2
}
```

위 예시는 관심 상품의 추가 필드 발췌이며 최상위 success/data와 기존 상품·페이지 필드는 그대로 반환한다.

## 집계 기준

하트 수는 현재 post_favorites의 상품별 관계 수다. 본인 관계도 포함하고 기존 사용자·상품 유일 제약과 등록·해제 정책을 따른다. 채팅방 수는 chat_rooms의 상품별 보관된 방 수다. 메시지가 없는 방 및 buyerDeletedAt/sellerDeletedAt으로 참여자가 숨긴 방도 포함한다. 같은 상품·구매자·판매자의 방을 재사용하면 수는 늘지 않는다. 물리 삭제한 방은 집계에서 빠지므로 영구 누적 통계는 아니다.

성공한 집계에서 관계가 없는 상품은 숫자 0을 반환한다. DB 조회 실패는 예외로 전파하며 0으로 위장하지 않는다. 사용자별 관심 목록의 인증 범위는 JWT로 결정한다. 집계는 숫자만 반환하며 관심 사용자나 채팅 참여자를 노출하지 않는다.

## 조회 및 동시성

조회할 페이지의 상품 ID를 모아 관심 관계·채팅방을 각각 GROUP BY 집계한다. 두 관계를 직접 조인하지 않으므로 하트 3개·방 2개·여러 이미지가 있어도 수치가 곱해지지 않는다. 빈 페이지에서는 집계를 생략한다. 매퍼는 상품과 미리 조회한 집계값만 조합하며 DB를 호출하지 않는다.

상세·검색·판매자·관심 목록 GET은 REPEATABLE_READ 읽기 트랜잭션을 사용한다. 페이지·전체 수·두 집계값은 같은 DB 스냅샷에서 읽고, 동시 변경은 다음 요청에서 반영한다. 상품 등록·수정의 기존 쓰기 트랜잭션과 권한·거래 상태 검증을 사용한다.

페이지마다 집계 SQL은 두 번 추가된다. 기존 조건의 관심 목록 100상품 검증은 인증 포함 SQL 7회, 검색은 8회 이하, 판매자 목록 25상품은 7회 이하를 검증한다. 이미지 배치 조건에 따른 기존 쿼리 수 변동과 구분한다.

새 테이블·컬럼·환경변수·DDL은 없다. 관심 관계의 post_id 인덱스와 채팅방의 post_id 선두 유일 제약이 이미 정의되어 있다. 운영 데이터 규모의 실행 계획과 응답 시간은 측정하지 않았다.

## 검증

H2 및 격리 PostgreSQL의 기존 관심 등록·해제·중복·인증·삭제·이미지 서명·SQL 횟수 회귀를 실행한다. 추가 HTTP 검증은 상세·검색·내 상품·판매자 상품·관심 목록·수정 응답의 3개 하트/2개 방 일치, 0 기본값, 빈/숨긴 방 포함, 등록 시각 구분 및 관심순 페이지 정렬을 확인한다. PostgreSQL 별도 연결에서 관심 관계 삭제와 채팅방 추가를 집계 직전에 커밋해 현재 관심 페이지의 이전 스냅샷과 다음 조회의 변경 반영을 검증한다.
