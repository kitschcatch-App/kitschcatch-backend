# 결제 상태 복구·웹훅·안전한 재시도 작업 설계

- 작성일: 2026-09-16.
- 이슈: [#29](https://github.com/kitschcatch-App/kitschcatch-backend/issues/29).
- 작업 브랜치: `feat/29`.
- 기준 코드: `origin/develop`의 `669924f1951b5f8b01e6a70f1c1c4bc3467479e8`.
- 문서 상태: 구현 진행 중. 핵심 모델·PG 조회·복구·웹훅·재시도 흐름은 구현됐고, 운영 PG 연동과 일부 고급 복구 시나리오는 후속 검증이 필요하다.

## 1. 목표와 범위

PG에서는 승인 또는 취소가 끝났지만 서버에는 `PROCESSING`으로 남은 결제를 복구한다. 같은 요청이 반복되거나 웹훅과 복구 작업이 동시에 실행돼도 중복 결제 없이 결제·주문·상품 상태가 실제 PG 결과와 일치해야 한다.

현재 지원하는 카드 결제의 승인·전액 취소를 대상으로 PG 재조회, 웹훅 수신, 주기적 복구, 실패 확정 후 재시도를 구현한다. 기존 상품 예약 15분, 주문당 결제 한 건, 주문 스냅샷을 유지한다. 추가 결제 수단, 반품·부분 환불, 주문 취소 업무 전체는 후속 이슈 범위다.

## 2. 현재 코드에서 재사용할 부분

| 코드 | 현재 역할 | 변경 방향 |
| --- | --- | --- |
| `OrderService` | 주문·READY 결제 생성 및 상품 예약 | 첫 승인 시도도 같은 트랜잭션에서 준비한다. |
| `PaymentService` | 승인·취소 외부 호출 조율 | 시도 단위 실행과 공통 결과 반영을 사용한다. |
| `PaymentTransactionService` | 짧은 트랜잭션으로 상태 변경 | 사용자 명령과 내부 복구의 진입점을 분리하고 상태 반영 규칙을 공유한다. |
| `OrderReservationService` | 상품 → 주문 → 결제 잠금, 예약 해제 | 실패 확정 결제의 만료를 지원하고 불확실 결제를 계속 보호한다. |
| `TossPaymentsClient` | 승인·취소 | 결제 조회, 구조화된 오류, 요청별 멱등키를 지원한다. |
| `PaymentRepository` | 주문당 결제 한 건과 잠금 | 시도 조회·복구 작업과 연결한다. |
| `SecurityConfig` | 사용자 JWT 인증 | 웹훅의 정확한 메서드·경로만 인증 예외로 추가한다. |

현재 `PROCESSING`은 승인과 취소를 구분하지 않는다. 승인 오류와 통신 오류도 동일한 예외로 변환한다. `GET /api/payments/{paymentId}`는 DB 조회만 수행하고 `approvedAt`은 서버 반영 시각이다. 이 차이를 복구 설계에 반영한다.

## 3. 지켜야 할 조건

1. 미확정 PG 작업이 있는 동안 새 승인 시도를 만들거나 상품 예약을 해제하지 않는다.
2. 결제 상태 변경은 상품 → 주문 → 결제 → 시도 순서로 잠근다. 외부 HTTP 요청 중에는 DB 잠금을 유지하지 않는다.
3. PG 응답의 주문 번호·결제 키·금액과 로컬 시도를 대조한다. 웹훅의 상태나 앱의 실패 보고만으로 금전 상태를 확정하지 않는다.
4. 현재 시도와 상태 버전을 확인한 뒤 결과를 반영한다. 이미 반영한 성공 응답은 같은 결과를 반환한다.
5. 결제·주문·상품 상태와 시도 처리 결과는 하나의 DB 트랜잭션에서 반영한다.
6. 재시도는 원래 예약 만료 시각을 연장하지 않는다. 승인 시작 전에 유효했던 예약은 PG 응답이 늦었다는 이유로 성공 반영을 거절하지 않는다.
7. 만료·취소는 해당 주문의 예약 소유권을 확인한다. 과거 시도나 과거 주문의 이벤트가 새 주문의 상품을 해제할 수 없다.
8. PG 조회가 계속 불가능하면 자동으로 실패 처리하지 않는다. 보호 상태와 운영 확인 기록을 유지한다.

## 4. 결제와 시도 모델

### 4.1 Payment: 사용자에게 보여 주는 결제 한 건

`payments.order_id` 유일 제약과 공개 `paymentId`를 유지한다. 기존 `READY`, `PROCESSING`, `SUCCESS`, `CANCELED`에 `FAILED`를 추가한다. `FAILED`는 승인 실패가 확정됐음을 뜻하며 취소 실패에는 사용하지 않는다.

추가 필드는 `currentAttemptId`, 상태 변경용 `stateVersion`, `recoveryState(NONE/PENDING/REVIEW_REQUIRED)`, `lastVerifiedAt`이다. `stateVersion`은 JPA 버전 필드로 구현하고 PG 요청 전후의 버전 비교에도 사용한다. 행 잠금이 도메인 쓰기를 직렬화하고, 버전은 잠금 밖에서 얻은 오래된 결과를 가려낸다.

취소 중에는 기존 응답 호환을 위해 결제 `PROCESSING`을 유지하되, 응답의 `processingOperation=CANCEL`로 승인 중과 구분한다. 주문은 `PAID`, 상품은 `SOLD_OUT`을 유지한다. 확정된 취소 실패는 시도에 기록하고 결제는 `SUCCESS`로 복귀한다.

### 4.2 PaymentAttempt: 승인·취소 시도 이력

`payment_attempts`를 추가한다. 승인 시도와 취소 시도는 `operation(CONFIRM/CANCEL)`으로 구분한다.

| 필드 묶음 | 저장 내용 |
| --- | --- |
| 식별 | 내부 PK, 공개 `attemptId`, `paymentId`, 결제별 증가 `sequence`, `operation` |
| 연결 | 재시도 원본 `sourceAttemptId`, 취소 대상 `approvalAttemptId` |
| PG 요청 | `pgOrderId`, `paymentKey`, 서버 확정 금액, 취소 사유, 요청 본문 해시, `pgIdempotencyKey`, 인증 설정 지문(비밀키 원문 제외) |
| 상태 | `PREPARED`, `PROCESSING`, `UNKNOWN`, `SUCCEEDED`, `FAILED`, `EXPIRED` |
| 증거 | PG 상태·오류 코드, 실패 확정 근거, 요청·완료·PG 승인·PG 취소 시각 |
| 복구 | `nextCheckAt`, 조회 횟수, `leaseToken`, `leaseUntil`, 상태 버전 |

`PREPARED`는 승인 요청을 보내기 전이며, `UNKNOWN`은 전송 여부 또는 최종 결과가 불확실한 상태다. 새 승인 시도를 준비하면 집계 결제는 `READY`, 승인·취소 시도가 `PROCESSING/UNKNOWN`이면 집계 결제는 `PROCESSING`이다. 실패 후 재시도 준비는 이전 시도의 실패 기록을 유지한다. 원문 PG 오류나 카드 정보 전체는 저장하지 않는다. 필요한 오류 코드와 정제한 설명만 보존한다.

DB에는 공개 시도 ID, `(payment_id, sequence)`, PG 멱등키의 유일 제약을 둔다. 승인 시도의 `pgOrderId`와 비어 있지 않은 `paymentKey`는 각각 유일하게 하고 취소 시도는 같은 PG 결제를 참조할 수 있게 한다. PostgreSQL 부분 유일 인덱스로 승인 시도에만 제약을 적용한다. `(source_attempt_id, operation)` 유일 제약은 같은 실패 시도로부터 새 시도가 두 개 만들어지는 것을 막는다. 결제별 활성 시도(`PREPARED/PROCESSING/UNKNOWN`) 하나도 부분 유일 인덱스로 보장한다. FK와 서비스 검증으로 연결된 시도가 같은 결제에 속하는지 검사한다. 복구 후보에는 `(next_check_at, id)`, 수신함에는 `(processing_status, next_check_at, id)` 인덱스를 둔다.

`Payment.paymentKey`와 `PurchaseOrder.pgPaymentKey`는 현재 승인된 결제 또는 진행 중인 승인 키를 나타내며, 과거 키는 시도 이력에 남긴다. 승인 실패 후 새 시도를 준비할 때 실패한 키를 다음 승인에 재사용하지 않는다. 취소 결과는 승인 시도의 과거 성공 기록을 지우지 않는다.

### 4.3 내부 주문과 PG 주문 번호

내부 `orderId`는 계속 `PurchaseOrder.orderNumber`를 뜻한다. 첫 승인 시도의 `pgOrderId`는 기존 앱과의 호환을 위해 내부 주문 번호와 같게 둔다. 실패 확정 후 새 시도는 서버가 새로운 `PG-<UUID>`를 발급한다. 취소는 성공한 승인 시도의 PG 주문 번호·결제 키를 사용한다.

앱에는 `orderId`와 `pgOrderId`를 구분해 반환한다. 새 시도마다 앱이 `pgOrderId`로 결제창을 열고 다시 인증해야 하며, 서버의 `/retry` 호출 자체가 새 승인을 실행하지는 않는다. 시도별 PG 번호를 두는 것은 이전 실패 세션의 재사용에 의존하지 않기 위한 이 프로젝트의 설계 결정이다. 앱이 승인 성공 콜백의 `orderId`를 내부 주문 번호로 덮어쓰지 않도록 연동 계약에 명시한다.

## 5. PG 결과 판정과 상태 전이

토스는 결제 키와 주문 번호를 통한 조회를 제공한다. 이 설계에서는 저장된 결제 키 조회를 우선하고, 키가 없을 때는 시도의 PG 주문 번호를 사용한다. 응답의 `totalAmount`, `balanceAmount`, `status`, 승인·취소 시각과 거래 식별자를 복구에 활용한다. [코어 API 근거](https://docs.tosspayments.com/reference).

| 현재 작업 | 확인한 결과 | 반영 |
| --- | --- | --- |
| 승인 진행·불확실 | 유효한 `DONE` | 시도 성공, 결제 `SUCCESS`, 주문 `PAID`, 상품 `SOLD_OUT`. |
| 승인 진행·불확실 | 유효한 `CANCELED`, 잔액 0 | 승인 후 취소까지 끝난 결과로 결제·주문 취소 및 해당 예약 해제. 승인 이력과 취소 사실을 함께 보존한다. |
| 승인 진행·불확실 | 유효한 `ABORTED` 또는 `EXPIRED` | 승인 실패 확정. 예약이 유효하면 결제 `FAILED`로 유지하고, 만료됐으면 주문 종료와 예약 해제를 같은 트랜잭션에서 처리한다. |
| 승인 응답 | 문서·계약 테스트로 확정된 승인 거절 코드 | 해당 요청의 실패 근거를 기록하고 동일한 실패 확정 경로를 사용한다. |
| 취소 진행·불확실 | 유효한 `CANCELED`, 잔액 0 | 취소 시도 성공, 결제·주문 `CANCELED`, 해당 예약 해제. |
| 취소 진행·불확실 | `DONE`만 조회됨 | 취소 결과는 여전히 불확실하다. 판매 완료와 복구 대기를 유지한다. |
| 취소 진행 | 해당 취소 요청의 최종 거절 확인 및 PG `DONE` 재확인 | 취소 시도 실패, 결제 `SUCCESS` 복귀. 새 취소는 명시적 사용자 요청으로만 시작한다. |
| 로컬 결제 성공 | PG에서 전액 취소 확인 | 관리자 PG 취소 등 외부 변경도 같은 전액 취소 복구 규칙으로 반영한다. |
| 모든 작업 | 통신 실패, 5xx, 429, 처리 중, 조회 결과 없음 | 불확실 상태 유지. 조회 재예약. |
| 모든 작업 | 식별자·금액 불일치, 부분 취소·지원 밖 상태 | 자동 재승인·예약 해제 차단, `REVIEW_REQUIRED` 기록. |

실패 코드는 HTTP 4xx 전체로 묶지 않는다. 최초 승인 거절 후보는 `REJECT_CARD_PAYMENT`, `REJECT_CARD_COMPANY`이며, 구현 단계의 응답 계약 테스트에서 해당 요청의 최종 실패로 분류되는지 확인한다. `ALREADY_PROCESSED_PAYMENT`, `ALREADY_PROCESSING_REQUEST`, `PROVIDER_ERROR`, 인증·설정 오류, `NOT_FOUND_PAYMENT`는 새 승인 허용의 근거로 삼지 않는다. 검증되지 않은 코드는 기본적으로 복구 대기다. [오류 코드 근거](https://docs.tosspayments.com/reference/error-codes).

PG 시각은 오프셋을 포함해 해석하고 저장 시간대로 정규화한다. 실제 승인 시각과 로컬 반영 시각을 분리한다. 이미 확정된 승인 시각은 중복 이벤트 때문에 갱신하지 않는다.

일반적인 카드 상태 흐름과 모순되는 결과는 위 표보다 운영 확인 규칙을 우선한다. 로컬에서 미결제로 만료한 주문에 PG 승인이 발견되거나 이미 다른 주문이 상품을 소유하면 이전 주문의 성공·예약 해제를 자동 반영하지 않는다. `CANCELED`만 보고 과거 승인 사실을 새로 만들지 않고 PG 승인 시각·거래 기록으로 확인한다.

## 6. 외부 호출과 동시성

### 6.1 승인·취소 공통 실행

1. 짧은 트랜잭션에서 권한·상태·예약을 확인하고 시도, 요청 내용, PG 멱등키를 먼저 저장한다. 시도를 `PROCESSING`으로 전환한다.
2. 커밋한 뒤 PG를 호출한다. 컨텍스트에는 시도 ID, 상태 버전, PG 주문 번호, 금액, 결제 키를 담는다.
3. 새 트랜잭션에서 같은 잠금 순서로 다시 읽고 시도·버전·예약 소유권을 검증한 뒤 결과를 반영한다.
4. 이미 같은 결과가 반영돼 있으면 성공 응답을 재사용한다. 그 사이 다른 작업이 진행됐다면 오래된 응답을 쓰지 않고 최신 상태 반환 또는 재조회를 예약한다.

외부 호출 전 프로세스가 죽어도 `PROCESSING`이 DB에 남으므로 복구 후보가 된다. 실제 전송 여부를 증명할 수 없으면 조회 결과 없음만으로 실패 처리하지 않는다. DB 커밋 실패로 오류 분류를 저장하지 못한 경우도 기존 `PROCESSING`을 근거로 다시 조회한다.

### 6.2 복구 작업 점유

시도별 `leaseToken/leaseUntil`을 짧은 트랜잭션에서 갱신해 웹훅 작업자와 스케줄러가 같은 시도를 동시에 조회하는 빈도를 제한한다. PG 호출 후에는 유효한 토큰과 상태 버전을 가진 작업자만 결과를 반영한다. 점유가 만료돼 새 작업자가 인계받으면 이전 작업자의 응답은 폐기하고 다음 조회에서 수렴시킨다. 로컬 정상 승인 응답이 먼저 상태를 확정해도 오래된 복구 결과가 덮어쓰지 못한다.

웹훅 수신함의 행 점유는 별도 짧은 트랜잭션으로 끝낸다. 수신함 잠금을 보유한 채 상품을 잠그거나 외부 API를 호출하지 않는다. 복구 반영 후 수신함 완료 기록 전에 죽으면 다시 실행해도 상태 변경은 중복 적용되지 않는다.

정상적으로 종료된 이전 시도의 실패·만료 알림은 현재 시도를 변경하지 않는다. 이전에 실패 확정한 시도에서 실제 `DONE`이 발견되는 모순은 무시하지 않는다. 현재 결제에 운영 확인 상태를 설정하고 새 승인·예약 해제를 막으며 양쪽 시도의 증거를 보존한다. 자동으로 현재 시도를 성공 처리하거나 임의 환불하지 않는다.

### 6.3 멱등키와 재전송

새 명령을 만들 때 PG 멱등키를 생성해 영속화한다. 같은 명령의 재전송은 키·요청 본문·PG 주문 번호·결제 키를 모두 유지한다. 실패가 확정된 뒤 새 사용자 시도를 만들 때만 새 키를 사용한다.

PG의 멱등키 유효 기간은 15일이다. 결과가 불확실한 기존 작업이 그 기간을 넘으면 새 키로 자동 재전송하지 않는다. 조회와 운영 확인만 허용한다. API 키 교체도 PG 측 멱등성 범위에 영향을 주므로 진행 중 명령의 인증 설정 변경 시 재전송을 중지하고 조회로 확인한다. [멱등키 근거](https://docs.tosspayments.com/reference/using-api/authorization).

첫 구현에서 불확실한 승인 작업은 조회로만 복구한다. 불확실한 취소는 먼저 조회하고, 계속 `DONE`일 때 기존 사용자 취소 의도를 이행하기 위해 같은 요청·멱등키로 제한적으로 재전송할 수 있다. 새 취소 시도를 만들지는 않는다. 기존 시도의 최초 요청 시각이나 키가 확실하지 않으면 재전송을 금지한다.

## 7. API와 앱 연결 계약

### 7.1 결제 재시도 준비

`POST /api/payments/{paymentId}/retry`는 구매자 JWT를 요구한다. 요청 본문은 `{ "failedAttemptId": "ATT-..." }`이며, 실패한 시도 식별자가 중복 요청의 기준이다. 금액·주문 번호를 앱에서 받지 않는다.

- 성공 조건: 해당 구매자의 현재 승인 시도가 실패 확정 상태이고, 주문 `PENDING`, 상품 `RESERVED`, 예약 소유권 일치, 예약 기한 미도달, 운영 확인 상태 없음.
- 기존 실패 시도에 대한 재호출은 새 시도 생성 조건을 검사하기 전에 기존 후속 시도를 조회해 응답한다. 현재 후속 시도가 `PREPARED`이고 예약이 유효할 때만 `OPEN_PAYMENT_WINDOW`를 반환한다. 처리 중·완료·만료됐거나 더 새 시도가 있으면 최신 결제 상태와 `nextAction=NONE`을 반환해 오래된 결제창을 열지 못하게 한다.
- 기존 요청 재호출이 아닌 신규 요청에서 처리 중·취소 완료·판매 완료·기한 만료·시도 불일치는 새 시도 없이 409로 거절한다. 타인의 결제는 기존 조회 정책처럼 404로 처리한다.
- 응답은 공통 `ApiResponse`의 200으로 통일하고 `paymentId`, 내부 `orderId`, `attemptId`, `pgOrderId`, `amount`, `reservationExpiresAt`, `status`, `nextAction=OPEN_PAYMENT_WINDOW`를 반환한다.
- 예약 기한은 원래 값을 유지한다. 재시도 준비 후 앱이 이탈한 `PREPARED` 시도는 PG 승인 호출이 없으므로 기존 미결제 만료 규칙으로 종료할 수 있다.

### 7.2 기존 API 보완

- 주문·결제 생성 응답에 `attemptId`, `pgOrderId`, `reservationExpiresAt`을 추가한다. 기존 `orderId` 의미는 바꾸지 않는다.
- 승인 요청에 `attemptId`를 추가한다. 초기 시도에 한해 기존 앱의 필드 누락을 허용한다. 재시도부터는 반드시 요구한다. 이전 키·다른 시도·다른 PG 주문 번호의 승인 요청은 거절한다.
- 동일 시도·동일 키의 승인 중복 요청은 완료됐다면 기존 결과, 처리 중이면 202와 현재 상태를 반환한다. 외부 승인을 새로 실행하지 않는다.
- PG 통신 결과가 불확실한 승인·취소는 실패 확정 응답 대신 202와 `PROCESSING`을 반환한다. 공통 응답에 accepted 생성 경로를 추가한다.
- 취소 재호출은 처리 중이면 같은 시도를 반환하고, 이미 전액 취소됐으면 기존 완료 결과를 반환한다. 확정 실패 후 새 취소 요청만 새 시도를 만든다.
- `GET /api/payments/{paymentId}`는 DB 상태 조회로 유지한다. 응답에 `attemptId`, `processingOperation`, `recoveryState`, `retryAllowed`, `reservationExpiresAt`, `lastVerifiedAt`, 정제된 `failureCode`를 추가한다. 조회마다 PG를 호출하지 않는다.
- 앱은 202를 결제 실패로 표시하지 않고 조회를 반복한다. `retryAllowed`는 안내값이며 실제 재시도 권한은 POST에서 다시 검사한다. 예약 만료 시 새 주문이 필요함을 별도 오류 코드로 알린다.

추가 API 오류 코드는 처리 중, 재시도 불가, 오래된 시도, 운영 확인 필요를 구분한다. 외부 PG 원문 오류와 비밀키를 응답에 노출하지 않는다. 모바일 소스는 이번 저장소 범위에 없으므로 DTO와 Swagger, 연동 문서로 계약을 제공하고 실제 앱 적용은 별도로 검증한다.

## 8. 웹훅 수신과 보안

`POST /api/payments/webhooks/toss`에 `PAYMENT_STATUS_CHANGED`만 등록한다. 이 카드 결제 이벤트에는 지급대행용 HMAC 서명 헤더를 적용할 수 없다. `CANCEL_STATUS_CHANGED`는 해외 비동기 결제 전용이므로 국내 카드 취소 복구의 전제로 삼지 않는다. [웹훅 이벤트 근거](https://docs.tosspayments.com/reference/using-api/webhook-events).

사용자 JWT 예외는 정확한 POST 경로로 한정한다. 이 경로에 사용자 인증이 없다는 사실이 요청 본문의 신뢰를 뜻하지 않는다. 서버 시크릿 키로 조회한 PG 결과만 상태 변경의 근거로 사용한다.

1. JSON 형태·크기·필수 식별자·지원 이벤트를 검사한다. 요청 경로 또는 본문에 담긴 URL로 외부 호출하지 않는다.
2. 알려진 PG 주문 번호·시도와 연결되는지 확인한다. 알 수 없는 주문은 금전 상태 변경 없이 제한된 진단 기록만 남긴다.
3. `payment_webhook_events`에 수신 기록을 커밋한 뒤 200을 응답한다. DB 저장 실패는 5xx로 응답해 PG가 재전송할 수 있게 한다. PG 조회는 수신 응답 전에 실행하지 않는다.
4. 내부 작업자가 기록을 읽고 공통 복구 서비스를 호출한다. PG 조회 실패는 수신함 재처리 대상으로 남긴다.

수신함에는 내부 ID, 전송 ID, 이벤트 타입·시각, PG 주문 번호·결제 키, 의미 있는 필드의 해시, 수신 횟수, 처리 상태, 재처리 시각, 점유 정보, 정제된 오류만 저장한다. 처리 상태는 `RECEIVED/PROCESSING/RETRY_WAIT/PROCESSED/IGNORED`로 구분하고, `PROCESSING` 점유 만료 건을 다시 처리한다. 전체 Payment 원문에 포함될 수 있는 개인정보는 저장하지 않는다.

중복 식별은 전송 ID와 이벤트 해시를 함께 사용한다. 재전송 때 전송 ID가 달라져도 의미가 같은 이벤트는 합칠 수 있다. 같은 ID에 다른 내용이 오면 충돌을 기록하고 후속 정상 이벤트를 영구 차단하지 않는다. 이벤트 시각은 상태 순서의 확정 근거로 사용하지 않는다. 서명 없는 웹훅이므로 중복 제거만으로 보안을 보장하지 않으며, 최종 보호는 PG 재조회와 상태 전이 검증이다.

잘못된 JSON은 400, 지원하지 않는 이벤트와 이미 저장한 중복 이벤트는 상태 변경 없이 200으로 처리한다. 알려진 시도의 조회 요청은 합치고 요청 크기·처리량을 제한한다. 웹훅이 유실되거나 잘못된 이벤트가 먼저 와도 주기적 복구가 영향을 줄인다. PG 재전송이 종료된 이후에도 수신함의 미처리 기록은 남는다. [웹훅 연결 근거](https://docs.tosspayments.com/guides/v2/webhook).

## 9. 주기적 복구와 예약 만료

`PaymentRecoveryScheduler`가 오래된 `PROCESSING/UNKNOWN`, 기한이 된 재조회, 미처리 웹훅을 대상으로 실행된다. 성공 결제에 대한 취소 웹훅도 복구 대상이므로 후보를 `PROCESSING` 결제에만 한정하지 않는다. 웹훅 유실 후 외부에서 취소된 결제도 찾을 수 있도록 성공 결제에 대한 느린 순환 조회를 별도로 둔다. `(lastVerifiedAt, id)` 커서로 분할하고 오래된 결제도 순환에 포함해 최근 결제만 반복하지 않는다.

초기 설정 제안은 아래와 같으며 테스트 환경에서 처리량을 확인해 조정한다. 새 스케줄러의 시작 여부를 기존 주문 만료 스케줄러에 의존시키지 않는다.

| 설정 | 초기값 | 목적 |
| --- | --- | --- |
| `app.payments.recovery.enabled` | false | 마이그레이션·키 확인 후 환경별 활성화. |
| `scan-delay` / `batch-size` | 30s / 50 | 불확실 결제 복구 후보 조회. |
| `processing-grace` | 60s | 진행 중 정상 HTTP 호출과의 불필요한 경합 완화. |
| `lease-duration` | 60s | 재시작·다중 인스턴스에서 작업 인계. |
| `retry-initial-delay` / `retry-max-delay` | 30s / 30m | 지수 증가 및 지터로 PG 재조회 부하 제한. |
| `review-after` | 24h | 장기 미확정 건의 운영 확인 표시. 예약 해제 기준이 아니다. |
| `success-scan-delay` / `success-batch-size` | 1h / 50 | 성공 결제의 외부 취소 누락 점검. |
| PG 연결 / 응답 타임아웃 | 3s / 10s | 무한 대기 방지. PG 호출별 적용. |

실패 횟수 때문에 후보를 영구 폐기하지 않는다. 운영 확인 표시 후에도 낮은 빈도의 조회를 유지한다. 후보 처리 한 건의 오류가 전체 배치를 중단하지 않게 하며, 가장 오래된 동일 건 때문에 다른 후보가 밀리지 않도록 `nextCheckAt`을 갱신한다. DB 점유와 PG 조회·취소 재전송에 각각 제한된 처리량을 둔다.

예약 만료 저장소 쿼리와 서비스의 재검증 조건을 함께 변경한다. 주문 `PENDING`이고 기한이 지난 `READY/PREPARED` 또는 실패 확정 결제만 종료한다. 모든 시도에 미확정 작업이 없는지, `REVIEW_REQUIRED`가 아닌지 다시 확인한다. 예약 만료 시 미결제 시도는 `EXPIRED`, 집계 결제와 주문은 기존 계약대로 `CANCELED`로 두어 PG 전액 취소와의 차이를 시도 이력에서 보존한다.

## 10. 코드 구성과 구현 순서

기존 `domain/order` 패키지 안에서 확장한다. 별도 메시지 브로커나 분산 잠금 인프라는 도입하지 않고 PostgreSQL에 저장한 작업 기록과 잠금을 사용한다.

| 단계 | 주요 변경 | 검증 결과물 |
| --- | --- | --- |
| 1. 계약·모델 | 상태 enum, PaymentAttempt, PaymentWebhookEvent, 요청·응답 DTO, DB 제약 | 상태 전이·중복 시도·스키마 테스트. |
| 2. PG 어댑터 | 조회 API, 응답 확장, 오류 분류, 멱등키 인자, 타임아웃 | HTTP 요청·오류·응답 검증 테스트. |
| 3. 공통 복구 | PaymentRecoveryService와 트랜잭션 서비스, 버전·시도 검증, 시각 반영 | 승인·취소 유실 및 DB 실패 복구 테스트. |
| 4. 사용자 흐름 | 첫 시도 생성, 재시도 준비, 승인·취소 중복 응답, 조회 DTO | 실제 HTTP·JWT·권한·예약 경계 테스트. |
| 5. 비동기 경로 | 웹훅 컨트롤러·수신함·작업자·스케줄러, 예약 만료 확장 | 중복·역순·재시작·동시 실행 테스트. |
| 6. 적용 준비 | 수동 SQL, 운영·앱 연동 문서, 기존 데이터 복구 정책 | PostgreSQL 마이그레이션·회귀·Toss 테스트 연동 증거. |

각 단계는 구현·테스트가 함께 완결되는 논리 단위로 커밋한다. 새 소스 파일에는 필수 지시문 이후 한 줄 한국어 역할 주석을 둔다. 구현 커밋은 이슈 번호와 한글 메시지를 사용한다.

## 11. 기존 데이터와 적용 절차

`src/main/resources/db/manual/029_payment_recovery.sql`을 제공한다. 기존 #27 SQL을 수정하지 않는다. 기존 배포 데이터에 대한 자동 DDL 갱신 대신 백업과 쓰기 중단 후 수동 트랜잭션 적용을 기준으로 한다.

- 사전 검사: 주문당 중복 결제, 승인 결제 키 중복, 금액·주문·상품 소유권 불일치, `PROCESSING`의 키 누락을 확인한다. 모순 데이터는 임의 정정하지 않고 적용 중단 또는 명시적 격리 대상으로 보고한다.
- `READY`는 첫 `PREPARED` 승인 시도로 보완한다. `SUCCESS`는 승인 성공 이력으로 만들고 PG 번호는 기존 주문 번호를 사용한다.
- `PROCESSING + PENDING`은 승인 미확정, `PROCESSING + PAID`는 취소 미확정 후보로 보완하되 이 분류가 PG 결과의 확정은 아님을 기록한다. 취소 후보에는 성공 승인 참조도 만든다.
- 기존 PG 멱등키는 코드에서 사용한 `confirm-<paymentKey>`와 `cancel-<paymentKey>`를 보존한다. 최초 요청 시각이 없으면 유효 기간을 추정하지 않고 조회 전용으로 복구한다.
- `CANCELED`는 실제 PG 취소와 미결제 예약 만료가 섞여 있을 수 있다. 키·승인 시각 등 증거로 구분하고, 판별할 수 없으면 과거 기록의 불확실성을 표시한다. 가짜 취소 거래를 만들지 않는다.
- 기존 예약 기한 NULL은 자동 생성하지 않는다. 상태 조회·기존 결과 복구는 허용하되 기한을 확정할 수 없는 주문의 새 재시도는 막는다.
- 새 시도의 PG 시각은 `Instant`와 PostgreSQL `timestamptz`로 보존한다. 기존 `LocalDateTime` 컬럼의 시간대는 배포 설정을 확인한 뒤 변환 규칙을 정하며, 과거 값을 일괄 UTC로 재해석하지 않는다.
- 제약·인덱스 생성과 backfill을 한 트랜잭션으로 검증한다. 실패 시 기존 데이터와 스키마가 보존되는지 테스트한다.
- 새 서버를 복구 비활성 상태로 배포한 뒤 테스트 키·웹훅 등록·기존 후보를 확인하고 활성화한다. 운영 적용은 별도 실행 작업이다.
- 신규 PG 시도가 생긴 뒤 구버전 서버는 이를 이해하지 못한다. 단순 바이너리 롤백을 하지 않고 쓰기·작업자를 중단한 상태에서 DB와 진행 중 PG 시도를 확인한다. 시도 이력을 삭제하는 다운 마이그레이션은 제공하지 않는다.

## 12. 검증 계획과 완료 기준

| 시나리오 | 반드시 확인할 결과 |
| --- | --- |
| 승인 성공 후 응답 유실 / DB 실패 | PG 재승인 없이 성공 복구, 상품 판매 완료, 실제 승인 시각 보존. |
| 취소 성공 후 응답 유실 / DB 실패 | 전액 취소 확인 후에만 상품 판매 가능, 다른 주문의 예약 유지. |
| HTTP 전송 직전 프로세스 종료 | 미확정 시도 유지, 조회 결과 없음만으로 실패·예약 해제 금지. |
| 웹훅 중복·순서 역전·일반 응답과 경합 | 한 번 반영, 취소 완료가 성공으로 되돌아가지 않음. |
| 웹훅 저장 직후 / 상태 반영 직후 재시작 | 수신함 재처리, 상태 중복 변경 없음. |
| 여러 작업자·점유 만료·늦은 응답 | 이전 토큰·버전 결과가 최신 상태를 덮어쓰지 않음. |
| 승인 실패 확정 후 동시 재시도 | 후속 시도 한 건, PG 번호 한 개, 기존 결제 행 유지. |
| 이전 시도의 실패·성공 이벤트 | 정상 과거 실패는 무시, 모순 성공은 운영 확인과 새 승인 차단. |
| 재시도 준비·승인 시작과 예약 만료 경합 | 기한 후 신규 승인 차단, 기한 전 시작한 미확정 승인 보호. |
| 취소 중 PG 조회가 DONE | 임의 성공 복귀·새 승인 없음, 동일 취소 재전송 규칙 준수. |
| 장기 장애·키 교체·멱등키 기간 경과 | 새 멱등키로 미확정 명령 재실행 금지, 조회·운영 확인 유지. |
| 외부 전액 취소 웹훅 유실 | 성공 결제 순환 조회로 취소 복구. |
| 위조 이벤트·식별자·금액 불일치·타인 접근 | 금전 상태 변경 차단, 민감 정보 비노출. |
| 기존 데이터 SQL 정상·충돌 fixture | 정상 보완 및 제약 생성, 충돌 시 전체 롤백. |

시간 경계와 backoff는 주입한 `Clock`으로 검증한다. HTTP 대역과 실제 DB 트랜잭션을 사용하고, PG 호출 횟수와 시도 수·상태·예약 소유권을 함께 단언한다. 동시성 검증에서는 PostgreSQL을 사용한다.

후속 구현에서 실행할 기본 명령은 `./gradlew test`와 `./gradlew build`다. 신규 복구 통합 테스트는 격리된 PostgreSQL을 지정하는 전용 환경 변수를 지원하게 만들고, 기존 예약 통합 테스트도 같은 환경에서 회귀 검증한다. 테스트 DB는 테이블 생성·삭제가 가능한 전용 DB만 사용한다.

Toss 테스트 환경에서는 새 PG 주문 번호로 재인증 → 승인 → 조회 → 취소 → 웹훅 수신을 확인한다. 테스트 키·수신 가능한 HTTPS 주소·웹훅 등록이 필요하다. 장애 주입으로 PG 응답 유실과 로컬 DB 실패를 별도로 검증한다. 대역 테스트 통과, 실제 PG 연동, 운영 배포는 서로 다른 증거로 기록한다.

완료 기준은 이슈 #29의 장애 상황에서 중복 승인 없이 상태가 실제 결과에 수렴하고, 불확실 상태에서 재시도·재판매가 차단되며, 기존 예약·결제 기능이 유지되는 것이다. 실제 PG에서 자동으로 확정할 수 없는 사례는 보호 상태와 운영 확인 대상으로 남아야 한다.
