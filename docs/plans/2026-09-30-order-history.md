# 거래 상세와 구매·판매 내역 구현 계획

- 이슈: [#43](https://github.com/kitschcatch-App/kitschcatch-backend/issues/43).
- 브랜치: `feat/43`, 기준 develop `1a3bab6` (#42 병합).
- 범위: 거래 당사자의 상세 및 본인 구매·판매 목록 조회. 취소·배송·환불·구매 확정·정산 신규 기능과 운영 배포는 제외한다.

## 명세와 계약

| API | 응답·권한 |
| --- | --- |
| `GET /api/orders/{orderId}` | 공개 주문 번호로 조회. 구매자 또는 주문 스냅샷의 판매자만 접근. 주문 상태·금액·상품·구매자·판매자·결제 요약. |
| `GET /api/users/me/purchase-orders` | JWT 사용자의 구매 목록. `content/page/size/totalElements/totalPages`. |
| `GET /api/users/me/sale-orders` | 주문 스냅샷의 sellerId가 JWT 사용자와 같은 판매 목록. 구매자 요약 포함. |

- Notion [상세](https://app.notion.com/p/3c1ee6172f5680b3833fdeb1e6c1b18e), [구매](https://app.notion.com/p/3c1ee6172f5680b0b46cd67440ae3917), [판매](https://app.notion.com/p/3c1ee6172f5680e79679c49450e8977c)의 필드 구조를 유지한다.
- 상세 `status`와 목록 `orderStatus`는 주문 상태다. 결제의 `status/paymentStatus`와 구분한다. 목록의 선택 `status` 필터는 `PENDING/PAID/CANCELED/REFUNDED`만 허용한다. 생략은 전체, 빈 문자열·공백·소문자는 오류다.
- `page=0` (0~10000), `size=20` (1~100). 생성 시각 DESC, 내부 ID DESC. 빈 목록과 범위 밖 페이지는 200이다.
- `orderId`는 내부 숫자 ID가 아닌 기존 `ORD-...` 주문 번호다. 길이 5~50의 영문·숫자·하이픈이며 ORD- 접두어를 요구한다. 생성 예시의 짧은 번호와 기존 UUID 번호 모두 허용한다.
- 인증 누락·유효하지 않거나 DB에 없는 사용자: 401 `AUTH_004`. 조회 조건 오류: 400 `COMMON_001`, 주문 번호 형식 오류: 400 `COMMON_002`, 주문 없음: 404 `ORDER_001`, 타인 주문 접근: 403 `ORDER_004`.
- 원문의 403 `ORDER_002`는 기존 409 예약 오류와 충돌하므로 새 코드로 분리한다. Swagger와 저장소 문서에 차이를 명시한다.

## 데이터와 조회

- 기존 상품 ID·상품명·판매자 ID/닉네임·금액 스냅샷을 사용한다. 구매자 닉네임과 대표 이미지 객체 키를 주문 생성 시 추가 저장한다. 첫 이미지는 sortOrder, ID 순으로 선택한다.
- `043_order_history.sql`로 두 스냅샷 컬럼과 구매자·판매자별 최신순/상태별 조회 인덱스를 추가한다. 기존 주문은 최초 적용 당시 사용자·이미지 값으로 보완하며 실제 과거 값을 복원했다고 주장하지 않는다. 재실행 때 이미 보완한 스냅샷을 바꾸지 않는다.
- 결제는 left join하여 주문과 한 SQL에서 읽는다. 결제 행이 없는 과거 주문도 제외하지 않고 null로 표시한다. 컬렉션과 현재 판매글·사용자 정보를 반복 조회하지 않는다.
- 대표 이미지 URL은 저장한 객체 키를 기존 이미지 URL 설정으로 조합한다. HEAD/GET 등 S3 요청이나 PG 호출은 하지 않는다. 객체 보존 자체는 이번 범위 밖이다.
- 조회는 읽기 전용이며 예약 만료·결제 복구를 유발하지 않는다. DB에 저장된 현재 상태를 반환하고, 처리 중인 결제는 처리 종류와 복구 상태도 보여준다.

## 검증·커밋·완료

계획 → 스냅샷 모델 → 수동 SQL → 조회 쿼리·입력 정책 → 상세 응답·서비스 → 구매/판매 목록 → HTTP/Swagger → HTTP 테스트 → PostgreSQL 검증 → 문서 순으로 논리 단위 커밋한다.

실제 HTTP·JWT·DB로 당사자 권한, 상태·결제 없는 주문, 필터·정렬·페이지, 판매글 수정·소프트 삭제 및 프로필 변경 후 스냅샷, 조회 무부작용과 N+1 방지를 확인한다. 격리 PostgreSQL에서 수동 SQL의 기존 데이터 보완·재실행·인덱스와 같은 HTTP 계약을 검증한다. 기존 주문·결제 테스트를 포함한 전체 테스트와 빌드를 실행한다.

완료 후 Obsidian에 작업 기록과 환경 변수 노트를 따로 저장하고, 템플릿에 맞춰 develop 대상 Open PR을 생성한다. 새로운 환경 변수는 추가하지 않으며 기존 DB·JWT·이미지 URL 설정과 테스트용 변수는 구분해 기록한다.
