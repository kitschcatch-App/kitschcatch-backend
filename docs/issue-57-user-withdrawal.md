# 이슈 #57 회원 탈퇴 계약과 보존 정책

## API와 계정 종료

- `DELETE /api/users/me`는 인증 Principal의 본인 ID만 사용한다. 쿼리나 JSON의 타인 ID는 사용하지 않는다.
- 성공: HTTP 200, `{"success":true}`. 데이터·종료 계정의 이메일·소셜 ID·거래 ID를 응답하지 않는다.
- 진행 또는 결과 확인이 필요한 거래: HTTP 409, `USER_057_001`. 구체적인 타인 거래 정보는 노출하지 않는다.
- 종료 계정이나 없는 계정의 access token: 다음 인증 필요 HTTP 요청부터 HTTP 401, `AUTH_004`. STOMP CONNECT·SEND·SUBSCRIBE에서도 종료 상태를 확인한다.
- 트랜잭션에서 사용자 행을 잠그고 `withdrawn_at`을 기록한다. users를 물리 삭제하지 않는다.
- 닉네임은 `탈퇴한 사용자`, 이메일은 UUID 기반 `@account.invalid` 주소로 대체한다. 닉네임 중복 키·프로필 이미지 키·프로필 등록 시각은 해제한다. 이메일 대체값은 외부로 발송하지 않는다.
- 모든 사용자 refresh token 행을 삭제한다. 로그인과 refresh는 사용자 잠금을 먼저 획득하고 현재 DB 종료 상태를 재확인해 새 토큰이 탈퇴 뒤 저장되지 않도록 한다.
- 이미 인증을 통과한 동일 계정 탈퇴 요청은 내부적으로 멱등 처리한다. 종료 후 기존 토큰으로 다시 요청하면 401이다.
- 소셜 제공자 종류와 subject는 종료 계정의 tombstone으로 유지한다. 동일 subject 재로그인은 401이며 새 사용자 생성·기존 계정 복구를 하지 않는다. 새로운 이메일로 기존 tombstone을 덮어쓰지 않는다.
- 기준 브랜치에는 카카오만 존재한다. #53의 네이버·Apple도 동일 사용자 잠금과 종료 상태 검사, tombstone 조회 정책을 통합해야 한다. 아직 없는 제공자 구현은 복사하지 않았다.
- login nonce는 로그인 전 생성되는 익명 challenge라 사용자 FK가 없다. 사용자별 삭제는 불가능하며 다른 사람의 nonce도 삭제하지 않는다. OIDC 검증을 통과한 nonce는 REQUIRES_NEW 트랜잭션에서 소비하고 종료 계정 로그인을 거절해도 재사용되지 않는다. 사용하지 않은 nonce는 기존 TTL에 따라 만료한다.

## 거래 차단 기준

구매자 `user_id` 또는 주문 당시 `seller_id`인 모든 거래를 검사한다. 결제 성공만으로는 탈퇴를 허용하지 않는다.

| 범위 | 차단 기준 |
| --- | --- |
| 주문 | CANCELED·REFUNDED·PURCHASE_CONFIRMED 이외의 상태. PENDING·PAID는 차단한다. |
| 구매 확정 | 정산이 없거나 COMPLETED가 아니면 양 당사자 모두 차단한다. |
| 환불 | 요청 식별자가 있고 REQUESTED·PROCESSING·NULL 또는 알 수 없는 상태면 차단한다. COMPLETED·REJECTED·WITHDRAWN은 확정된 상태로 취급한다. |
| 정산 | 식별자가 있고 WAITING·PROCESSING·UNKNOWN·FAILED·NULL 또는 알 수 없는 상태면 차단한다. COMPLETED만 허용한다. |
| 결제 | 결제 행 부재, PROCESSING, 복구 NONE 이외 또는 NULL, 종료 주문과 결제 상태 불일치이면 차단한다. 취소·환불 주문은 CANCELED·FAILED, 정산 완료 구매 확정 주문은 SUCCESS여야 한다. |
| 결제 시도 | PROCESSING·UNKNOWN은 차단한다. CANCEL의 PREPARED·FAILED도 결과가 미확정/실패한 취소로 보아 차단한다. |

과거 CONFIRM FAILED만 남아 있고 주문은 CANCELED, 현재 복구 상태 NONE이면 탈퇴할 수 있다. 실패한 진행 주문이나 복구 대기 상태는 계속 차단한다. 과거 실패 기록을 삭제해서 탈퇴를 허용하지 않는다. 정산 FAILED나 취소 시도 FAILED의 해소는 #45 상태 처리·운영 확인 범위이며 이 기능이 강제로 성공 처리하지 않는다.

## 동시성과 기록 보존

- 신규 주문은 구매자·판매자 사용자 행을 ID 오름차순으로 잠근 후 상품을 잠근다. 계정 종료 여부를 검사하고 주문을 생성한다. 탈퇴가 먼저 커밋하면 신규 주문은 거절된다. 주문이 먼저 커밋하면 탈퇴는 409이다.
- 탈퇴는 본인 사용자 → 관련 상품 ID 오름차순 → 주문 ID 오름차순과 그 결제 순서로 잠근 후 DB의 현재 거래 상태를 검사한다. #45의 상품 → 주문 → 결제 잠금과 순서를 맞춘다. 기존 결제·환불·복구의 진행 트랜잭션이 확정되기 전에는 상태 검사를 통과하지 않는다.
- 본인 판매글은 같은 트랜잭션에서 숨긴다. 상품 생성도 사용자 잠금을 사용한다. 상품·상품 이미지·주문·결제·시도·웹훅·환불·정산·지급 수취인·채팅방·메시지와 FK를 물리 삭제하지 않는다.
- 주문의 구매자/판매자 닉네임·상품·이미지·금액·지급 목적지 스냅샷은 수정하지 않는다. 인증된 거래 상대방의 주문 상세에서 계속 조회한다. 현재 사용자 프로필은 익명화된다.
- 채팅 내용과 판매글 본문, 주문 스냅샷에는 당사자가 기록한 개인정보가 남을 수 있다. 이 기능은 임의로 과거 거래 기록을 편집하거나 법적 보존 기간을 확정하지 않는다.
- 보존 근거·기간·만료 시 파기·별도 분쟁 접근 권한은 정책/법무 검토 후 결정해야 한다. 현재는 자동 파기·S3 객체 삭제·소셜 unlink를 실행하지 않는다.
- 관련 거래가 많은 계정은 전체 관련 상품/주문 잠금을 사용해 응답 시간이 길어질 수 있다. 운영 규모에서 측정·제한 정책 검토가 필요하다.
- 백그라운드 PG 재조회가 종료 이후 새로운 외부 이상을 발견하는 운영 시나리오는 보존 기록을 통한 운영 처리 대상이다. 종료 계정을 자동 복구하지 않는다.

## 병합 통합 의존성

- base는 `feat/45`, 초기 기준 SHA는 `85ff03c669ea360cf9b71f05749ea6a08a76accc`다. #45의 공유 미커밋 변경은 포함하지 않았다.
- #49의 공개 프로필/소개/사용자 ID 필드는 병합 시 같은 종료·비노출 정책에 포함해야 한다.
- #50의 알림함·기기 토큰·발송, #51의 관심 상품, #52의 팔로우 테이블은 현재 기준에 없다. 통합 시 삭제/익명화 대상과 이벤트 발송 억제를 연결해야 한다. 현재 존재하는 관심 매장 기록과 관련 FK는 보존한다.
- #53의 추가 소셜 제공자는 위 tombstone·사용자 잠금 정책에 연결해야 한다.
- HTTP 인증에는 종료 상태 DB 조회가 요청당 1회 추가된다. 거래 목록/상세의 기존 N+1 방지 검증은 이 1회만 반영한다.
- 실제 S3·Toss 연동은 사용자 지시로 미완료를 유지한다. 운영 DB 적용·배포·실제 지급·객체 삭제·메시지/푸시는 실행하지 않는다.
- 제공된 Notion 원문은 접근되지 않아 기존 코드의 공통 응답·인증 계약과 이슈 #57을 기준으로 200/409/401을 정했다. 외부 명세는 수정하지 않았다.

## 수동 SQL과 검증

`src/main/resources/db/manual/057_user_withdrawal.sql`은 users에 nullable TIMESTAMPTZ 종료 시각만 추가한다. 운영에서는 스키마 백업·검토 후 애플리케이션 변경보다 먼저 적용한다. 기존 계정은 NULL로 활성 상태를 유지한다. 반복 적용 가능하며 자동 마이그레이션·운영 적용은 이 작업에 포함하지 않는다.

채팅 전용 PostgreSQL 인스턴스와 무작위 issue57 스키마를 사용한다. JDBC URL은 `ISSUE57_TEST_DB_URL`, 사용자와 암호는 `ISSUE57_TEST_DB_USERNAME`·`ISSUE57_TEST_DB_PASSWORD`로 전달한다. PostgreSQL 테스트는 Hibernate가 만든 종료 컬럼을 제거한 후 실제 수동 SQL을 두 번 적용해 HTTP·FK·스냅샷·잠금 계약을 다시 검증한다.

검증 실행 결과와 독립 리뷰의 대상 SHA·발견 사항·해결 여부는 PR에 기록한다. 환경 변수가 없는 기존 PostgreSQL 선택 테스트와 실제 외부 연동·운영 검증은 별도로 표시한다.
