# 결제 웹훅 동시 재전달과 수신함 처리

추적 이슈는 [#126](https://github.com/kitschcatch-App/kitschcatch-backend/issues/126)이다.

웹훅 수신은 전송 ID와 이벤트 종류·본문 해시를 중복 기준으로 삼는다. 기존 경로는 중복 조회와 저장을 나눠 처리했고, 전송 ID에만 DB 유일 제약이 있었다. 수신 경로를 단일 삽입으로 바꾸고 두 키를 DB에서 보장한다. 중복 행은 삽입하지 않으며, 기존 행의 처리 상태와 처리 횟수는 그대로 유지한다. 정상적으로 수신한 재전달에도 HTTP 200을 반환한다.

## 검증

격리 PostgreSQL과 실제 수신 컨트롤러를 연결한 MockMvc로 같은 결제 이벤트 두 건을 동시에 전달했다. 전송 ID가 같은 경우와 다른 경우를 각각 검증했다. 각 요청이 200을 받고 수신함에는 `RECEIVED` 한 행만 남았다.

웹훅 워커를 실행하면 PG 대역을 한 번 조회해 수신함 한 행을 `PROCESSED`로 변경했다. 결제·주문·상품·시도 상태는 `SUCCESS / PAID / SOLD_OUT / SUCCEEDED`였고 구매자와 판매자의 성공 알림은 각각 한 건이었다. 처리 뒤 같은 이벤트를 재전달하고 워커를 다시 실행해도 수신함 행, PG 조회, 알림은 늘지 않았다.

검증 범위는 보완한 로컬 코드의 컨트롤러·PostgreSQL·워커다. PG 조회는 테스트 대역을 사용했고 워커는 테스트에서 실행했다.

## 기존 DB 적용

기존 DB에는 `db/manual/126_payment_webhook_inbox_deduplication.sql`을 새 수신 코드보다 먼저 적용한다. 짧은 수신 쓰기 중단 시간을 확보하고 백업한다. SQL은 수신함 테이블의 잠금을 최대 5초 기다리고, 잠금을 확보하면 한 트랜잭션에서 중복을 확인한 뒤 유일 제약을 추가한다. 과거 중복이 있으면 기존 행을 보존하고 적용을 중단하므로, 처리 이력을 대조한 뒤 다시 실행한다. 격리 PostgreSQL에서 정상 적용·재적용과 중복이 있는 경우의 원본 보존을 검증한다.

운영 DB와 배포는 이번 검증 범위 밖이다.

## 2026-11-12 결과

Java 21과 PostgreSQL 14.18에서 수신 통합 2건과 수동 SQL 검증 2건이 통과했다. CI와 같은 DB 환경 변수 구성을 사용한 로컬 `./gradlew --offline clean build --no-daemon --console=plain`에서 전체 테스트 1306개가 통과했다. 실패·오류·건너뜀은 모두 0개였다. 원자료는 작업 공간의 `build/payment-recovery-w/2026-11-12/`에 보존했다.
