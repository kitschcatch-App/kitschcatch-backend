# 장기 미확정 결제의 예약 점유와 조회 비용

추적 이슈는 [#126](https://github.com/kitschcatch-App/kitschcatch-backend/issues/126)이다. 대상은 `feat/126`의 `e64edfe` 앱 빌드다.

별도 구매자·판매자·상품을 만든 뒤 실제 주문과 승인 HTTP API를 호출한다. PG 대역은 승인 효과를 `DONE`으로 기록하고 승인 응답을 닫아 앱이 `202 PROCESSING`을 반환하게 한다. 준비 JVM에서는 복구 스케줄러를 끈다. 동일 DB와 JAR로 관측 JVM을 시작해 스케줄러를 켠다. 결제와 예약 상태를 SQL로 변경하지 않는다.

| 실행 조건 | 미확정 후보 | 관측 시간 |
| --- | ---: | ---: |
| `persistent`. GET이 계속 503을 반환한다. 별도로 승인하지 않은 일반 예약을 만료 대조군으로 둔다. | 1 | 17분 |
| `delayed`. 3건은 승인 효과 기록 2분 뒤, 3건은 10분 뒤에 DONE을 조회할 수 있다. 4건은 계속 503을 반환한다. | 10 | 17분 |
| `fast100`. 처음부터 GET이 DONE을 빠르게 반환한다. | 100 | 2분 |
| `mixed100`. 먼저 준비한 5건의 GET에서 읽기 제한이 발생하고 나머지 95건은 DONE을 빠르게 반환한다. | 100 | 2분 |

복구 스캔 30초, 배치 100, 예약 TTL 15분, 만료 스캔 60초, PG 읽기 제한 10초를 그대로 사용한다. 17분은 관측 JVM 준비 완료부터 센다. 실험 조건별로 한 번씩 실행한다. 조건끼리 같은 호스트와 PostgreSQL 인스턴스를 사용하되 스키마, 앱 JVM, PG 대역은 분리한다.

- 복구 지연은 PG가 DONE을 반환할 수 있는 시점부터 DB 확정을 처음 관측할 때까지다. 미해결 거래는 지연 통계와 별도로 집계한다.
- 미확정 예약 점유는 PG 대역의 승인 효과 기록부터 내부 확정 관측 또는 관측 종료까지를 센다. 종료 때 남은 예약은 주문 생성부터의 예약 나이도 별도로 기록한다.
- 비용은 조회 시작 횟수, 관측 분당 조회 수, PG 대역 응답 소요와 동시에 열린 GET 연결 수로 확인한다. 조회 수와 승인 POST 수를 구분한다.
- 적체는 조회 가능 시각이 지났고 활성 lease가 없는 후보를 샘플링한다. 시도 상태, 다음 조회 시각, 예약 만료 여부를 함께 기록한다.

## 실행

[A1 실행 환경](payment-recovery-a1.md#실행)에서 프로필별로 새 결과 디렉터리를 지정한다.

```sh
./gradlew bootJar
PYTHONDONTWRITEBYTECODE=1 python3 scripts/payment_recovery_c.py \
  --profile persistent --jar build/libs/kitschcatch-backend-0.0.1-SNAPSHOT.jar \
  --db-port 55486 --db-user a1 --db-name kitschcatch_w126 \
  --out /tmp/kitschcatch-c-persistent
```

`manifest.json`, `scenario-results.csv`, `backlog.csv`, `events.jsonl`, 앱 로그를 보존한다. 17분 조건은 DB를 약 2초 간격으로, 100건 조건은 약 1초 간격으로 관측한다.

## 2026-11-12 결과

| 조건 | 관측 | 복구 / 미해결 | PG GET | 미확정 예약 점유 |
| --- | ---: | ---: | ---: | ---: |
| 지속 실패 1건 | 17분 | 0 / 1 | 5 | 17.15 예약·분 |
| 지연·실패 혼합 10건 | 17분 | 6 / 4 | 44 | 114.75 예약·분 |
| 빠른 조회 100건 | 2분 | 100 / 0 | 100 | 67.87 예약·분 |
| 선두 5건 타임아웃 100건 | 2분 | 95 / 5 | 101 | 154.32 예약·분 |

- 지속 실패 1건과 지연·실패 혼합의 4건은 기본 15분 기한이 지난 뒤에도 원래 예약을 유지했다. 종료 때 DB 예약 나이는 모두 약 21분 24초였다. 별도의 일반 예약은 DB 기준 15분 26초에 해제됐다. 장기 미해결 5건은 각각 GET 5회를 했고 `REVIEW_REQUIRED`로 전환되지 않았다.
- 2분 뒤 조회 가능해진 3건은 가용 시점부터 확정까지 중앙값 101.45초, 최댓값 101.52초가 걸렸다. 10분 뒤 조회 가능해진 3건은 중앙값 101.35초, 최댓값 101.38초였고 모두 예약 기한이 지난 뒤 확정됐다. 10건 조건의 GET 44회는 503 응답 38회와 성공 응답 6회였다.
- 100건에서 뒤쪽의 같은 95개 순번을 비교하면 정상 복구 지연 중앙값은 40.59초에서 90.49초로 49.89초 늘었다. 혼합 조건의 GET 101회는 성공 95회, 응답 없는 조회 5회, 종료 시 진행 중 1회였다. 응답 없는 다섯 조회는 대역에서 합계 50.01초를 차지했다.
- 장기 관측에서는 DB 시계가 실행기 단조 시계보다 약 254초 더 진행했다. 17분 관측 창, 가용 지연, 예약·분은 실행기 시계로, 실제 예약 나이와 15분 기한 경과는 DB 시각으로 산정했다. 짧은 혼합 조건에서는 같은 비교에서 차이가 0.01초였다.

각 조건에서 승인 POST와 승인 효과는 후보당 한 건이었다. 같은 조건을 반복해 지연의 분포나 운영 SLA를 추정하는 검증은 남아 있다. 공용 실행기 변경 후 A1도 1회 통과했다. 원자료는 작업 공간의 `build/payment-recovery-c/2026-11-12/`에 보존했다.
