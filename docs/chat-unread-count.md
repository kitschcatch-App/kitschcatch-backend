# 채팅방 목록 미읽음 메시지 수

이슈 #75, 브랜치 `feat/75`, 기준 `develop`의 `34d466b`.

## API 계약

`GET /api/chat-rooms`의 각 채팅방에 정수 `unreadCount`를 추가한다. 인증된 사용자에게 상대방이 보낸 메시지 중 `isRead=false`인 텍스트·이미지 메시지를 집계한다. 내 메시지와 이미 읽은 메시지는 제외한다. 메시지가 없으면 필드를 생략하지 않고 `0`을 반환한다.

```json
{
  "success": true,
  "data": [{
    "chatRoomId": 101,
    "postId": 10,
    "postTitle": "키링 판매",
    "opponentId": 2,
    "opponentNickname": "판매자",
    "lastMessageContent": "판매 중입니다.",
    "lastMessageAt": "2026-11-04T10:30:00",
    "unreadCount": 3
  }]
}
```

기존 BUYER/SELLER 역할 및 postId 필터와 참여자별 삭제 조건을 유지한다. 집계 사용자 ID는 JWT에서 가져오며, 반환 대상 방 ID에 대해서만 집계한다. 빈 목록은 `data: []`이고 집계 조회를 생략한다. 기존 정렬과 인증·입력 오류 계약을 유지한다.

## 읽음 처리와 동시 요청

목록 조회는 읽음 상태를 변경하지 않는다. 기존 WebSocket `/pub/chat-rooms/{chatRoomId}/read`에서 읽음 처리하고 `/sub/chat-rooms/{chatRoomId}/read`에서 결과를 받는다. 읽음 처리 완료 후 목록을 재조회하면 처리된 메시지는 집계에서 제외된다. 이후 새 메시지가 도착하면 미읽음 수는 다시 증가한다.

목록과 집계는 REPEATABLE_READ 읽기 트랜잭션으로 같은 스냅샷을 사용한다. 다른 연결에서 메시지를 읽음 처리해도 진행 중인 응답은 이전 상태를 유지하고 다음 요청에 반영한다. 읽음 처리에서 이미 선택한 메시지 ID만 갱신하는 기존 계약에 따라, 선택 후 도착한 새 메시지는 미읽음으로 남는다. 응답 이후의 실시간 화면 갱신은 앱에서 기존 채팅 이벤트와 재조회 계약을 연결한다.

## 조회와 데이터베이스

기존 메시지 읽음 상태를 사용하며 새 테이블·컬럼·환경변수·데이터 이관은 없다. 반환 대상 방 전체의 `chatRoomId, count`를 한 번에 조회해 응답에 조합한다. 채팅방마다 추가 조회하지 않는다. HTTP 인증 처리까지 포함한 25개 방 조회의 SQL 상한은 기존 3회에 집계 1회를 더한 4회다.

이번 변경에는 인덱스 DDL을 포함하지 않는다. 실제 서버 데이터 분포와 실행 계획을 측정하지 않았으므로 대규모 운영 데이터의 지연 시간은 별도 측정 대상이다. 기존 목록 API가 페이지 없이 전체 방을 반환하는 계약도 유지한다.

## 검증 범위

- 저장소: 상대방 미읽음만 집계하며 요청한 방 밖의 메시지를 제외한다.
- 서비스·컨트롤러: 0 기본값, 빈 목록의 집계 생략, 숫자 직렬화.
- H2 및 PostgreSQL 실제 HTTP/JWT: 구매·판매 역할, 상품 필터, 참여자별 삭제, 사용자별 다른 미읽음 수, 텍스트·이미지 혼합, 읽음 처리 후 감소와 새 메시지 후 증가.
- PostgreSQL 동시 연결: 목록 조회 도중 다른 연결의 읽음 커밋, 읽음 대상 ID 선택 후 새 이미지 메시지 도착.
- 기존 인증·권한·정렬 회귀 및 25개 방의 SQL 4회 이하를 검증한다.
