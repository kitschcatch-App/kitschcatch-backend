# 운영자 신고 심사

이슈 #107. 운영자가 신고를 조회하고 심사 결과를 기록한다. 심사 완료는 판단을 기록하는 단계다. 콘텐츠 숨김과 계정 제재는 별도 운영 정책으로 다룬다.

## 모바일 팀 전달

앱이 사용하는 기존 `POST /api/reports`, `GET /api/users/me/reports`, `GET /api/reports/{reportId}` 경로와 응답 필드를 사용한다. `status`에 다음 값이 올 수 있으므로 문자열을 제한하는 모델과 내 신고 화면을 함께 갱신한다.

| 상태 | 표시 문구 |
| --- | --- |
| `RECEIVED` | 접수됨 |
| `IN_REVIEW` | 검토 중 |
| `RESOLVED` | 검토 완료 |
| `DISMISSED` | 기각 |

접수 요청을 같은 내용으로 재전송하면 기존 신고 ID와 **현재 상태**가 돌아온다. 최초 접수 때만 `201`이고 동일 요청 재전송은 `200`이다. 알 수 없는 상태를 받은 경우 앱이 목록 전체를 파싱하지 못하는 일이 없도록 기본 문구를 사용한다. 만료된 신고는 목록에서 사라지며 상세는 기존과 같이 `404`다.

앱에서 신고 증거 메시지는 기존 계약대로 신고자가 최대 10개를 선택한다. 운영자 상세·처리 사유·처리자·채팅 스냅샷은 운영자 API에만 제공된다. 앱이 표시하는 `RESOLVED`는 제재 여부를 의미하지 않는다.

## 권한

활성 사용자의 기존 access JWT와 DB의 `report_reviewers` 활성 행이 필요하다. Spring Security가 `/api/admin/reports`와 하위 경로에서 DB 권한을 확인하고, 서비스에서도 다시 검사한다. 요청 본문이나 JWT의 역할 값으로 권한을 부여하지 않는다. 권한 회수 후 기존 토큰의 새 운영자 요청도 거절한다.

운영자가 신고자나 대상 사용자이면 목록에서 해당 건을 제외하고, 상세·증거·이력·변경 요청을 거절한다. 권한 부여·회수는 운영 DB의 제한된 세션에서 실행한다. 다음 명령의 계정 ID와 승인 근거는 실제 운영 값으로 지정한다.

```sh
psql -v reviewer_id=42 -v enabled=true -v reason='운영 승인 티켓 번호' -f scripts/report-reviewer.sql
psql -v reviewer_id=42 -v enabled=false -v reason='운영 권한 회수 티켓 번호' -f scripts/report-reviewer.sql
```

실제로 바뀐 권한만 `report_reviewer_events`에 DB 실행 주체·시각·사유를 기록한다. 탈퇴 계정에는 권한을 부여할 수 없다.

## 운영자 API

| 요청 | 동작 |
| --- | --- |
| `GET /api/admin/reports` | 상태·대상·사유·신고자·대상 사용자·접수 기간으로 조회 |
| `GET /api/admin/reports/{reportId}` | 설명, 접수 스냅샷, 검토 시작자·최종 처리자와 시각 |
| `GET /api/admin/reports/{reportId}/evidence/messages` | 접수 시 선택한 채팅 증거 |
| `GET /api/admin/reports/{reportId}/evidence/messages/{messageId}/image` | 해당 메시지의 이미지 바이트 |
| `PATCH /api/admin/reports/{reportId}/status` | 버전 기반 상태 변경 |
| `GET /api/admin/reports/{reportId}/history` | 접수 시각 및 버전순 상태 변경 이력 |

목록 파라미터는 `status`(복수 가능), `targetType`, `reasonCode`, `reporterId`, `targetUserId`, `from`, `to`, `page`, `size`다. `from` 이상, `to` 미만이며 ISO 8601 시각을 쓴다. 상태를 생략하면 `RECEIVED`와 `IN_REVIEW`를 반환한다. 오래된 접수 시각·ID 순으로 정렬한다. `page` 기본 0·최대 10000, `size` 기본 20·최대 100이다. 응답은 `content/page/size/totalElements/totalPages`이며 상세와 상태 변경 응답의 `report`도 같은 요약 구조다.

```json
{
  "status": "RESOLVED",
  "reason": "선택 메시지에서 반복적인 욕설을 확인했습니다.",
  "expectedVersion": 1,
  "requestId": "91a12c1b-12de-4d48-b33c-d60b327180ed"
}
```

`RECEIVED → IN_REVIEW → RESOLVED 또는 DISMISSED` 순서로 진행한다. 최종 결과에 사유가 필요하며 최대 1000자다. 다른 운영자가 검토를 이어갈 수 있다. 처리자와 시각은 서버가 결정하고 상태·버전·이력을 한 트랜잭션에서 저장한다. 변경 응답은 `report/historyId/replayed`다. 같은 운영자의 동일 요청을 재전송하면 이력을 추가하지 않고 기존 `historyId`와 현재 상태를 반환한다. 버전이 오래됐거나 요청 ID를 다른 내용에 재사용하면 `409`이므로 상세를 다시 조회한다.

- `401 AUTH_004`: 토큰 없음·만료 또는 탈퇴 계정.
- `403 REPORT_008`: 권한 없음 또는 본인 관련 신고.
- `404 REPORT_005`: 신고 없음·만료. `404 REPORT_010`: 조회할 수 있는 증거 없음.
- `409 REPORT_009`: 허용되지 않은 상태 전이, 버전 불일치, 요청 ID 충돌.
- `503 REPORT_011`: 이미지 저장소 설정 또는 조회 오류.

## 증거 범위와 보관

채팅 목록에는 선택한 최대 10개 메시지의 ID, 작성자 ID, 종류, 접수 당시 내용·작성 시각, 이미지 참조 여부를 반환한다. 선택 메시지가 없으면 빈 배열이다. 원본 메시지와 주변 대화를 다시 조회하지 않아 읽음 상태에 영향을 주지 않는다. 상세와 증거 열람은 운영자·신고·조회 종류·시각만 감사 기록에 저장한다. 이미지 조회는 저장소를 호출하기 전에 허용된 열람 시도를 기록한다.

이미지는 해당 신고의 스냅샷에 포함된 이미지 메시지에서만 읽는다. 설정된 버킷과 채팅방·작성자의 경로 및 서버 발급 파일명에 맞는 참조를 사용한다. 응답 크기는 최대 10 MiB로 제한한다. JPEG·PNG·GIF·WebP만 반환하며 캐시를 금지한다. S3 요청의 8초 제한은 본문 읽기에도 적용한다. 저장소에서 파일이 없다고 확인되거나 참조를 안전하게 매핑할 수 없으면 `404`다. S3가 접근을 거부하면 권한 부족과 파일 부재를 구별할 수 없으므로 `503`을 반환한다. 채팅에 이미 노출된 공개 URL의 접근 범위는 현재 저장소 정책을 따른다. [S3 GetObject 문서](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)

## 적용과 확인

1. 실행 중인 백엔드 버전과 대상 DB를 확인한다. DB를 백업한 뒤 `091_reports.sql` 적용 여부와 배포할 버전까지 필요한 선행 SQL을 확인한다. 미적용 SQL을 순서대로 적용하고 `107_report_reviews.sql`의 커밋, 심사 테이블·상태 제약과 기존 신고 보존을 확인한다. 기존 접수는 버전 0과 기존 접수 시각으로 이관한다.
2. 백엔드를 배포한 뒤 실행 JAR의 해시와 HTTPS OpenAPI의 운영자 경로를 확인한다. 시드니 개발 서버는 EC2의 Docker Compose로 실행된다. [GitHub Actions의 ECS 작업](development-deployment.md)과 EC2 배포 결과를 별도로 기록한다. 배포를 되돌릴 때도 신고와 심사 이력은 보존한다.
3. 신고자·대상과 별개인 테스트 계정으로 권한 부여 전 `403`, 부여 후 동일 토큰으로 목록 `200`을 확인한다. 테스트 신고에서 목록·상세·심사 변경·요청 재전송·충돌·이력을 확인한다. 검증에 실패한 경우에도 부여한 권한을 회수한다. 토큰이 여전히 유효한 상태에서 일반 사용자 API `200`과 운영자 API `403`을 확인한다.
4. 개발 버킷에 테스트 채팅 이미지를 정상 업로드 경로로 올리고 메시지를 신고에 첨부한다. 운영자 이미지 API의 `200`, `Content-Type`, `Cache-Control: no-store`와 원본 파일 해시 일치를 확인한다. 선택하지 않은 메시지는 `404`여야 한다. 상세·증거 목록·이미지의 감사 기록을 대조한다. 사용한 테스트 객체의 키를 기록하고 버전 관리가 켜진 버킷에서는 해당 객체의 버전과 삭제 마커까지 확인한다.
5. 기존 `expiresAt`에 따라 만료된 신고를 조회에서 제외한다. 정리 워커와 만료 후 재접수에서 이전 신고를 삭제할 때 심사 이력과 열람 감사 기록도 함께 삭제한다. 운영자 권한 부여·회수 이력은 별도로 관리한다.

테스트 신고와 채팅·상품·신고용 계정을 정리했다. 권한 감사 이력을 보존하기 위해 운영자 테스트 계정 두 개는 권한 회수 후 비활성 상태로 남겼다. S3 테스트 객체 두 개의 버전을 삭제하고 해당 키에 남은 버전과 삭제 마커가 없음을 확인했다. 임시 SSH 허용 규칙도 제거했다. DB 백업, 이전 Compose 릴리스 설정과 서버 검증 기록은 개발 서버의 제한된 백업 디렉터리에 보관했다.
