# 신고 접수

이슈 #91, 브랜치 `feat/91`, 기준 develop `bde8413`. 모든 API는 활성 계정의 access JWT가 필요하다. 신고자는 JWT에서 결정한다.

운영자 심사 API와 모바일 상태 표시 계약은 [운영자 신고 심사](report-review.md)를 참고한다.

## API

| 요청 | 계약 |
| --- | --- |
| `GET /api/reports/reasons?targetType=POST` | 해당 대상의 사유 코드·표시 문구·설명 필수 여부·최대 길이 목록. |
| `POST /api/reports` | 첫 접수 201, 동일 요청 재전송 200, 다른 내용의 중복 409. |
| `GET /api/users/me/reports?page=0&size=20` | 본인 신고 요약 목록. page 0~10000, size 1~100. |
| `GET /api/reports/{reportId}` | 본인 신고 상세. 타인의 신고와 없는 신고 모두 404. |

요청 예시:

```json
{"targetType":"CHAT_ROOM","targetId":45,"reasonCode":"HARASSMENT","description":"거절 이후 욕설을 보냅니다.","messageIds":[901,902]}
```

`targetType`은 USER, POST, CHAT_ROOM, STORE_REVIEW이다. ID는 양의 정수이고, 서버 관리 필드 및 알 수 없는 필드·잘못된 JSON 타입을 거부한다. 설명은 앞뒤 공백 제거 후 최대 1000 Unicode code point이며 OTHER는 비어 있을 수 없다. NUL을 거부한다. 채팅 신고에만 messageIds를 명시할 수 있고, 생략/null은 선택 없음이다. 최대 10개의 서로 다른 양의 정수이며 모두 해당 방의 메시지여야 한다. 메시지 ID의 입력 순서는 중복 판정에 영향을 주지 않는다.

최초 접수·재전송은 reportId, targetType, targetId, reasonCode, status, createdAt을 반환한다. 내 목록은 동일 요약 항목과 content/page/size/totalElements/totalPages이다. 상세는 description/messageIds를 추가한다. 내부 target_snapshot, 대상 사용자, 다른 신고자와 신고 건수는 반환하지 않는다. 목록은 접수 시각·ID 내림차순이다.

## 대상과 권한

자기 자신·본인의 게시글·본인의 매장 리뷰를 신고할 수 없다. 게시글은 미삭제이며 작성자가 활성 계정이어야 한다. 리뷰는 공개 상태(미삭제·미숨김·활성 작성자)여야 한다. 사용자 신고 대상도 활성 계정이어야 한다. 채팅은 참여자만 가능하며 상대는 서버가 결정한다. 기존 채팅 조회와 동일하게 참여 이력을 기준으로 하므로 차단 및 상대 탈퇴 후에도 가능하다. 비참여자는 존재 여부를 알 수 없는 404를 받는다. 거래 후기는 대상에 포함하지 않는다.

대상별 사유는 단일 ReportReasons 정의를 조회와 검증에 함께 사용한다. 최초 신고는 RECEIVED 상태로 기록한다. 접수는 차단·팔로우 변경·메시지 읽음·알림·콘텐츠 숨김·리뷰 별점 변경·자동 제재를 수행하지 않는다.

## 중복·동시성

보관 중인 `(reporter_id,target_type,target_id)`당 한 건이다. 정규화한 사유·설명·메시지 집합이 동일하면 기존 접수 시각과 ID를 반환한다. 다른 내용으로 덮어쓰지 않는다. 기존 접수는 원본 삭제 후에도 재전송/조회할 수 있다.

관련 사용자 행을 ID 오름차순으로 잠근 뒤 활성 상태를 확인하고 대상 행을 잠가 권한·공개 상태를 재검사한다. 사용자 잠금은 차단·팔로우·탈퇴·리뷰 변경과 같은 순서이며 게시글 쓰기는 해당 게시글 잠금과 직렬화된다. 대상 기록과 접수는 한 트랜잭션이다. 같은 신고자의 서로 다른 대상 접수도 신고자 행에서 직렬화하여 분/일 한도를 넘지 못한다. DB 고유 제약은 별도로 중복을 방지한다.

기본 새 접수 한도는 최근 60초 5건, 최근 86400초 20건이다. 같은 요청 재전송은 한도를 추가 소비하지 않는다. 초과는 429 REPORT_006이다. 계정별 제한이며 전체 트래픽 방어를 대체하지 않는다.

## 스냅샷과 개인정보

공개 프로필의 닉네임·아이디·소개·이미지 키, 게시글 제목·설명·가격·시각·이미지 참조, 리뷰 본문·별점·버전·시각·이미지 참조, 채팅방 정보 및 선택 메시지만 JSONB로 저장한다. 이메일·소셜 제공자 식별정보·토큰을 복사하지 않는다. 채팅 이미지 URL은 그대로 복사하지 않고 chats 경로가 있으면 쿼리를 제외한 참조 경로만 기록한다. 선택하지 않은 대화는 수집하지 않는다.

텍스트는 원본 수정·삭제 후에도 접수 당시 내용을 유지한다. 이미지 ID·키는 참조일 뿐 이미지 원본의 보존을 보장하지 않는다. S3 사본 생성과 신규 증거 파일 업로드는 없다. 기존 사진 정리 정책으로 삭제될 수 있다.

기본 보관은 접수 후 90일이며 expires_at을 지난 신고는 본인 조회에서 제외한다. 만료된 동일 대상 신고는 새 접수 트랜잭션에서 교체할 수 있다. 계정 탈퇴는 기존 익명화 정책을 사용하며 신고를 즉시 연쇄 삭제하지 않는다. 연결된 식별정보와 접수 시점 공개 정보가 보관 기한까지 남으므로 완전 익명화를 의미하지 않는다. 90일은 개발용 기본값이며 출시 전 운영 방침을 확정해야 한다.

정리 워커는 한 번에 최대 100개를 SKIP LOCKED로 삭제하며 DB 기록만 정리한다. 원본 콘텐츠/S3 파일을 삭제하지 않는다. 신고 본문·대화·토큰을 별도 로그에 기록하지 않는다.

## 오류

REPORT_001 대상 없음/접근 불가 404, REPORT_002 자기 신고 400, REPORT_003 대상에 허용되지 않는 사유 400, REPORT_004 다른 내용의 중복 409, REPORT_005 내 신고 없음 404, REPORT_006 한도 초과 429, REPORT_007 메시지 연결 오류 400이다. JSON 타입·알 수 없는 필드·파라미터 오류는 기존 COMMON 오류를 사용하고 인증은 AUTH_004이다.

## 배포

1. 기존 사용자·게시글·채팅·리뷰 스키마가 있는 DB에 `src/main/resources/db/manual/091_reports.sql`을 적용한다. 신규 테이블과 인덱스만 추가하며 SQL은 재실행 가능하다.
2. 앱을 배포한다. 추가 외부 서비스·S3 권한·유료 API는 필요 없다.
3. SQL 적용을 확인한 환경에서 `APP_REPORTS_CLEANUP_ENABLED=true`를 설정한다. 미마이그레이션 테스트/서버에 워커가 접근하지 않도록 기본값은 false다.
4. 네 대상의 접수·재전송·본인 조회·비참여자 거부와 워커 정리를 검증한다. 테스트용 신고/계정을 정리한다.

설정: APP_REPORTS_MINUTE_LIMIT=5, APP_REPORTS_DAILY_LIMIT=20, APP_REPORTS_RETENTION_DAYS=90(1~3650), APP_REPORTS_CLEANUP_ENABLED=false, APP_REPORTS_CLEANUP_DELAY=1m. 한도와 기한은 양수여야 하며 잘못된 설정은 기동 시 거부한다. 보관 설정 변경은 이후 새 접수에 적용하며 기존 expires_at을 소급 변경하지 않는다.

앱 롤백 시 테이블을 보존하고 정리 워커 설정을 끈다. 공개 트래픽을 받는 환경의 신고를 삭제하는 down SQL은 제공하지 않는다.

## 검증

실제 PostgreSQL의 격리 스키마에 SQL을 두 번 적용한다. ReportPostgresTest는 HTTP 인증·네 대상·입력 변조·타인 신고 접근·선택 메시지·차단/탈퇴 후 채팅 신고·재전송·원본 삭제 후 기록 유지·분/일 한도·6개 동시 접수·삭제 대기 후 상태 재확인·개인정보 제외·Unicode 경계·만료 정리와 재접수를 검증한다. CI에 ISSUE91_TEST_DB 환경 변수를 추가한다. 개발 서버 배포와 실제 모바일 화면 검증은 PR 범위 밖이다.

Java 21·PostgreSQL 14의 격리 로컬 DB에서 `./gradlew clean build --offline --console=plain --max-workers=1`을 완료했다. 전체 1387개 테스트, 실패 0·오류 0·건너뜀 0개이며 신고 PostgreSQL 통합 테스트는 9개다. 개발 DB와 S3에는 쓰지 않았다.
