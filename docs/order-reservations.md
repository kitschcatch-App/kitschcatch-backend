# 주문 예약과 중복 판매 방지

이슈 #27은 기존 주문·결제·상품 API에 예약 소유권과 거래 당시 정보 보존을 추가한다.

## 동작

- 주문 생성 시 상품을 잠그고 판매 가능 여부를 검증한다. 상품별 유효 주문 하나만 만들고 15분간 예약한다.
- 같은 주문으로 결제 생성 API를 다시 호출하면 기존 READY 결제를 반환한다. 결제수단/금액이 다르거나 처리 중이면 거절한다.
- 결제 승인 직전에 예약 소유권과 기한을 확인하고 paymentKey를 기록한다. DB 잠금을 해제한 다음 PG를 호출한다.
- PG 승인이 확인되면 결제 SUCCESS, 주문 PAID, 상품 SOLD_OUT을 함께 저장한다. PG 취소가 확인되면 결제와 주문을 CANCELED로 바꾸고 해당 상품을 ON_SALE로 복구한다.
- 60초 간격으로 최대 100개의 만료 후보를 조회한다. 각 주문을 별도 트랜잭션으로 다시 확인하고 PENDING/READY 상태인 해당 소유 주문만 해제한다. 처리량에 따라 실제 해제는 기한보다 늦을 수 있지만, 기한이 지나면 승인을 시작할 수 없다.
- 예약 및 결제 완료 주문이 있는 상품의 내용·이미지·가격·수동 상태 변경과 삭제를 차단한다. 주문 없는 수동 예약/판매 상태 관리 동작은 유지한다.
- 주문의 snapshotPostId, postTitle, amount, sellerId, sellerNickname은 생성 당시 값을 유지한다. 후속 거래 상세/내역 API는 이 값으로 거래 정보를 표시해야 한다.

## 오류와 복구

- POST_006(409). 거래 중인 상품 변경 또는 재주문 제한.
- ORDER_002(409). 상품 예약 소유권 또는 상품 상태 불일치.
- ORDER_003(409). 예약 시간 만료.
- 기존 판매 중이 아닌 상품 주문은 기존 BAD_REQUEST 응답을 유지한다.
- PG 오류, 응답 유실, 응답 검증 실패, 외부 승인 후 DB 저장 실패 시 PROCESSING을 유지한다. 해당 상품은 다시 판매하지 않는다. paymentKey로 PG 결과를 확인하고 후속 웹훅/재조회 복구 작업을 거쳐야 한다. 이번 변경은 자동 결제 복구나 새 재시도 API를 제공하지 않는다.
- 취소 결과가 불확실한 경우에도 상품을 SOLD_OUT으로 유지한다. PG가 취소했는지 확인하기 전 SUCCESS나 ON_SALE로 강제 복구하지 않는다.

## 기존 데이터베이스 적용

신규 빈 DB는 엔티티로 스키마를 생성할 수 있다. 기존 DB에는 애플리케이션의 주문·결제·상품 쓰기를 중단하고 백업 및 PG 결과 확인 후 `src/main/resources/db/manual/027_order_reservations.sql`을 한 번 적용한다. 자동 실행 스크립트가 아니다.

중복 활성 주문, 주문당 중복 결제, 삭제 상품의 활성 주문이 있으면 스크립트 전체가 실패하도록 했다. 실제 결제 결과에 따라 먼저 정리해야 하며 이 스크립트는 거래 데이터를 삭제하지 않는다. 기존 스냅샷은 현재 상품/프로필 정보로 보완되고 과거 값의 완전한 복원은 불가능하다. 기존 주문 만료 시각은 NULL로 두므로 PG 확인 없이 자동 취소되지 않는다.

설정은 `app.orders.reservation-ttl`(기본 15m), `expiration-scan-delay`(기본 60s), `expiration-enabled`(기본 true)이다. 스키마 적용과 기존 주문 확인을 마친 후 새 버전을 시작한다.

## 검증

`./gradlew test --tests '*OrderReservationIntegrationTest'`로 실제 H2 트랜잭션을 사용한 예약·승인·취소·만료·스냅샷·동시 요청을 검증한다.

동일 테스트를 격리된 PostgreSQL에서 실행하려면 `ISSUE27_TEST_DB_URL`, `ISSUE27_TEST_DB_DRIVER=org.postgresql.Driver`, `ISSUE27_TEST_DB_USER`를 설정한다. 테스트는 해당 DB의 테이블을 생성하고 삭제하므로 반드시 비어 있는 테스트 전용 DB를 사용한다. 운영/개발 공용 DB를 지정하지 않는다.
