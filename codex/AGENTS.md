# AGENTS.md

## 1. 프로젝트 개요

- 프로젝트명: `KitschCatch Backend`
- 성격: 서브 컬처 굿즈 탐색, 중고 거래, 오프라인 매장 정보 제공 플랫폼의 백엔드
- 현재 단계: Spring Boot 초기 부트스트랩 단계
- 목표: 상품 탐색, 거래, 결제, 매장 정보, 위치 기반 기능까지 확장 가능한 백엔드 구조 마련

## 2. 현재 저장소 상태

- 현재는 기본 Spring Boot 애플리케이션과 테스트 환경이 구성된 초기 상태다.
- 구현 완료 상태로 간주할 수 있는 것은 아래 수준이다.
  - Gradle Wrapper 구성
  - Spring Boot 실행 구조 구성
  - `spring-web`, `spring-data-jpa`, `spring-validation`, `spring-websocket` 의존성 추가
  - `application.yml`, `application-local.yml`, `application-dev.yml`, `application-prod.yml` 분리
  - 기본 컨텍스트 로딩 테스트 구성
- 아직 본격적인 도메인 모델, API, 엔티티, 인프라 구성은 들어가기 전 단계다.
- 문서나 코드 설명 시, 기획상 기능과 현재 구현된 기능을 혼동하지 않는다.

## 3. 기술 스택

- Java 21
- Spring Boot 4.0.5
- Gradle 9.4.1
- Spring Web
- Spring Data JPA
- Spring Validation
- Spring WebSocket
- PostgreSQL
- Lombok
- 테스트: Spring Boot Test, H2

## 4. 서비스 및 도메인 방향

- 이 프로젝트는 서브 컬처 굿즈의 탐색, 중고 거래, 오프라인 매장 정보 제공을 하나의 플랫폼에서 다루는 것을 목표로 한다.
- MVP 기준 주요 범위는 아래와 같다.
  - 사용자: 소셜 로그인, 프로필, 관심 상품/매장, 거래 내역
  - 상품 탐색: 목록 조회, 상세 조회, 거래 문의, 결제
  - 상품 관리: 판매글 CRUD, 판매 상태 관리
  - 매장/위치: 매장 운영 정보, 매장 상품 정보, 위치 기반 탐색
- 향후 확장을 고려해 `User`, `Product`, `Order`, `Payment` 등의 도메인을 중심으로 구조를 설계한다.
- 초기 구현에서도 이후 확장을 막는 임시 구조는 피한다.

## 5. 디렉터리 및 코드 구조 가이드

- 패키지는 역할이 드러나도록 명확하게 나눈다.
- 기본 방향은 아래와 같다.
  - `controller`: HTTP 요청/응답 처리
  - `service`: 비즈니스 로직
  - `domain` 또는 `entity`: 핵심 도메인 및 JPA 엔티티
  - `repository`: 데이터 접근
  - `dto`: 요청/응답 DTO
  - `config`: 설정 클래스
- API 요청/응답 DTO와 영속 엔티티를 직접 혼용하지 않는다.
- 컨트롤러에는 비즈니스 로직을 넣지 않는다.
- 검증은 가능하면 요청 DTO에서 Jakarta Validation으로 우선 처리한다.

## 6. 구현 원칙

- 변경은 작은 작업 단위로 나눈다.
- 한 커밋이나 한 변경에서 여러 목적을 섞지 않는다.
- 현재 코드베이스와 맞지 않는 과도한 추상화, 선제적 최적화, 불필요한 공통화는 피한다.
- Spring Boot 관례를 우선한다.
- 설정값, 비밀번호, 토큰, DB 접속 정보는 코드에 하드코딩하지 않는다.
- 설정이 늘어나면 `application.yml` 또는 `@ConfigurationProperties` 기반 구성을 우선 검토한다.
- 예외 처리와 로깅은 명확하게 작성하되, 초기 단계에서 불필요하게 큰 프레임워크를 만들지 않는다.
- 민감 정보는 로그에 남기지 않는다.

## 7. JPA 및 데이터베이스 주의사항

- 기본 DB는 PostgreSQL 기준으로 설계한다.
- 테스트는 H2를 사용해도 되지만, 실제 스키마/쿼리가 PostgreSQL과 충돌하지 않는지 항상 의식한다.
- 엔티티 연관관계는 꼭 필요한 방향으로만 둔다.
- 양방향 연관관계는 필요성이 명확할 때만 도입한다.
- 조회 기능을 구현할 때 N+1 가능성을 함께 점검한다.
- 지연 로딩에 의존하는 로직은 서비스 계층의 트랜잭션 범위를 명확히 한다.

## 8. 환경 및 배포 방향

- 개발과 운영 환경은 분리하는 방향으로 유지한다.
- 현재 저장소는 아래 설정 파일 구조를 사용한다.
  - `application.yml`: 공통 설정
  - `application-local.yml`: 로컬 개발 환경
  - `application-dev.yml`: 개발 서버 환경
  - `application-prod.yml`: 운영 환경
- 환경별 DB 접속 정보는 환경 변수로 관리한다.
- 로컬 실행 시에는 `SPRING_PROFILES_ACTIVE=local`을 기본으로 사용한다.
- 배포 자동화, 브랜치 전략, CI/CD는 이후 본격화되더라도 반복 가능한 절차를 깨지 않는 방향으로 변경한다.

## 9. 검증 원칙

- 문서 수정이 아닌 코드 변경이면 최소한 테스트 실행 여부를 확인한다.
- 기본 검증 명령은 아래를 우선한다.
  - `./gradlew test`
  - 필요 시 `./gradlew bootRun`
- 실행이나 테스트를 못 돌렸다면 이유를 반드시 남긴다.
- 환경 변수 부족 등으로 실행이 막히면 필요한 값을 함께 적는다.

## 10. Git 및 커밋 규칙

- 커밋은 반드시 작업 단위별로 진행한다.
- 커밋 메시지는 반드시 한국어로 작성한다.
- 커밋 메시지 형식은 반드시 `{type}: {한글 메시지}`를 따른다.
- 예시:
  - `feat: 상품 조회 API 추가`
  - `fix: 판매 상태 변경 검증 오류 수정`
  - `chore: 스프링 설정 초기화`
  - `docs: README와 AGENTS 문서 정리`
- 사용자가 명시적으로 요청하지 않은 변경은 임의로 되돌리지 않는다.
- PR 또는 작업 설명은 무엇을 왜 바꿨는지 한 줄로 요약 가능해야 한다.

## 11. 문서 관리 원칙

- README는 서비스 소개와 저장소 상태를 설명하는 문서다.
- AGENTS.md는 이 저장소에서 작업할 때 따라야 하는 규칙 문서다.
- 아래 상황에서는 README와 AGENTS.md를 함께 갱신하는 것을 우선 검토한다.
  - 프로젝트 구조가 확정되었을 때
  - 도메인 설계 원칙이 구체화되었을 때
  - 예외 응답, 로깅, 테스트 전략이 정해졌을 때
  - 환경 분리 및 배포 절차가 확정되었을 때
  - MVP 범위가 바뀌었을 때
